# Leak corpus

Every program here is compiled and run by `scripts/leak-check`, which `scripts/validate` calls.

Two backends measure the same corpus. `--fast` links each case with AddressSanitizer and LeakSanitizer; the default uses valgrind. They agree case by case, LSan's `Direct leak` is the counterpart of valgrind's `definitely lost`, both excluding blocks reachable only from another leaked block, but they are not supersets of each other: memcheck is stricter about reads of uninitialized memory, ASan about buffer overflows and use-after-free. Use `--fast` while iterating and the default before milestones, releases and any broad refactor of ownership, runtime or FFI. `scripts/validate` runs the slow one.

Cases whose cost has nothing to do with what a given change touches are split into their own scripts, all four of which `scripts/validate` runs, so the full gate still covers everything:

- `scripts/leak-check-fs`, the `fs-*` cases. They spend their time in syscalls, where valgrind's overhead is far worse than on ordinary compute: in one measured run `fs-glob-search-diff` alone ran over 18 minutes, more than every non-fs case put together. Run it when `tyrus:fs` changes, or when the ownership of native string and array results changes.
- `scripts/leak-check-repl` and `scripts/leak-check-jit`, the REPL's own leak regression (`repl_leak_loop`) and the JIT engine's (`jit_leak_loop`) are Rust unit tests, not `.tyr` files here. Run them when `src/repl.rs`/`src/compile.rs` change; they take ~9 minutes each regardless of what changed.

`scripts/leak-check` measures cases in parallel (`TYRUS_LEAK_JOBS`, defaulting to `nproc`) and builds into a target directory of its own, so it neither evicts nor is evicted by an ordinary `cargo build`. That isolation is not just for speed: an ordinary build running while the corpus was in flight once replaced the compiler underneath it with a mimalloc-linked one, and every case then reported `Invalid free()`, a whole run silently invalidated, because neither tool can see through mimalloc's arena.

- **`clean/`**, must report `definitely lost: 0 bytes`. A category that has been fixed lives here, and any regression fails the run.
- **`known/`**, still leaks. The script requires these to *keep* leaking: when one stops, it tells you to move the file to `clean/`, so a fix is never merged without locking it in.

`known/` shrinking to empty is the definition of done.

Programs are wrapped in a throwaway project by the script, so a file here is just the body of `src/main.tyr`. Each one loops 200 times: a leak of a few bytes per operation is invisible in a single run and fatal in a loop or a long-running server, so repetition is what makes it measurable.

## Closed on 2026-08-24: four ownership defects the fast backend could not see

The two `clean/` cases that corrupted memory under valgrind (and passed under `--fast`) turned out to be four separate defects. None of them leaked, which is why LeakSanitizer stayed quiet and why the corpus reported them as `CORRUPTED` rather than as a byte count. All four predate the change that found them; three were reproduced against the installed compiler as well as the working tree.

The route in every case was the same: reduce to a minimal program, get a symbolized stack from valgrind or AddressSanitizer, read the emitted IR, and only then change code.

### 1. `splice` cleaned its inserted temporary twice

`tyrus_array_splice_owned_strings` *clones* what it inserts, so the temporary array built for the inserted elements is still owned by the caller. Two cleanups claimed it: a branch inside the `splice` codegen, and the generic pending-owned-native-result cleanup that registers every array literal inside an `async` function. Both ran, and the second walked a buffer the first had already freed.

Removing the `splice` half rather than the generic one was deliberate. They were not equivalent: the `splice` half released element by element through `emit_async_cleanup_source_expression`, which declines to release a value it believes came from a named binding, wrong for a literal that owns its elements. With only that half in place the corpus stopped corrupting and started leaking 5015 bytes instead, which is how the difference was found.

Minimal reproducer: an `async` function that does `mutated.splice(1, 1, "delta")` and returns. No loop and no `await` needed.

### 2. `pop`/`shift` inside `async` leaked the element they removed

Revealed by fixing the first one: the double free had been *compensating* for a missing release elsewhere, so the corpus had been reporting zero.

`tyrus_array_pop` moves the removed element into a fresh heap box and returns the box. The synchronous path releases the element and then frees the box; the async path emitted a bare `free` on the box and left the element's own allocation behind. The cause is one condition: the release plan is `Deep` only when the receiver is a tracked owned array, and that check asked the *synchronous* ownership registry only. An async local keeps its mode byte in a registry of its own, so every `pop`/`shift` inside an `async` function fell to `ReleasePlan::Value`. One leaked string per call, 2400 bytes over 200 iterations.

### 3. An async closure released its captures twice

An async closure is lowered as an async function whose parameter list is `captures ++ declared`, so its captures arrive as leading frame parameters. The frame's drop glue released every "generic owned" parameter (`Mutex`, `RwLock`, `Semaphore`, `Sender`, `Receiver`) and the closure's environment drop released the same captures. One retain, two frees.

valgrind put it exactly: an invalid read inside `tyrus_mutex_free`, reached from `__tyrus_async_drop_*`, on a block whose "free'd at" stack was a previous `tyrus_mutex_free`. The frame borrows its captures; the environment owns them. This one has no small reproducer, the same closure in isolation ran 10/10 clean, and it took the full examples corpus to make the allocator reuse the memory.

### 4. An array literal did not take a reference to a named element

The narrowest and most general of the four, and the only one outside `async`.

An element named by a binding is not a temporary the literal can claim, so the literal was given a buffer-only release plan and stored the value as it stood. That gave one allocation two owners, and they disagreed the moment the array outlived the binding: `return [v]` had the callee release `v` at scope end and the caller release the same element when it dropped the array it received.

Taking a reference of its own is what the counted buffer is for, the binding keeps its reference, the array gets one, each side releases what it holds. A static element has no count to raise and is copied instead, which balances the same way.

The corpus case that caught it is named `generic-monomorphization`, but the defect has nothing to do with generics: the same `const wrapStr = (value: string): string[] => [value]` fails identically without them.

### What this says about the gate

`--fast` measures leaks. Three of these four were not leaks, and the fourth only became one after another was fixed. The default valgrind backend is the one that catches this class, and the README already said to run it before milestones, the lesson is that "the corpus is green" means less than it sounds when only the fast backend has run.

## Why a leak here matters

The failure mode is not untidiness. Every open category below leaks **per iteration** (measured at 20 and 200 iterations, all scale exactly 10×) so the cost grows without bound in a loop or a server. Leaking at process exit would be harmless; the operating system reclaims it.

## The rule ownership follows today

Ownership carries a **`ReleasePlan`**, recorded where ownership is *taken*, the only point at which an allocation is still distinguishable from a static value. `Deep` releases everything the type says is allocable, `Buffer` releases an array's buffer and leaves its elements alone, and `Fields` names the fields of an aggregate to release, each under its own plan.

The plan travels with the *binding*, not the type, because scope cleanup looks a value up by name and reads its declared type, and a type cannot say whether the parts were allocated. That is the whole reason this exists: `["a", "b"]` and `[a.toUpperCase(), b.toUpperCase()]` have the same type and opposite releases.

This replaced an all-or-nothing rule where an aggregate was claimed only when every allocable thing inside it came from an allocation. Anything mixed was left to leak, deliberately, because the release freed an aggregate's strings as a group and freeing a static one is corruption rather than a leak. Naming the fields is what made the mixed case expressible.

What a plan still cannot say is whether a value **escapes**. A buffer handed to a callee belongs to the callee, and the scope that built it must not release it, however precisely it can describe the release. `refused-owned-return` closed one shape of this (a callee whose `return`s are a genuine per-path mix of owned and borrowed) through a runtime bit read at the call site rather than a static plan, and `conditionally-owned-return-not-propagated` closed the next: that bit now survives being handed onward through any number of wrappers that return a conditionally-owned call's result unchanged, rather than stopping at the first one.

Freeing twice is worse than leaking. `scripts/leak-check` fails on an invalid free or invalid access before it looks at any byte count, in `known/` as well as `clean/`: a case there is allowed to leak and never allowed to corrupt.

Worse still is a program that stops working. Ownership changes sit on the paths that leave a scope, so they can break control flow rather than memory: releasing at a `throw` first reused the cleanup a `return` performs, which also unwinds the catch contexts, and every `catch` within reach of a `throw` silently stopped catching while every byte count stayed green. Cases therefore print their results as `value` / `assert: expected` pairs, and a mismatch fails the run before valgrind is consulted at all.

## What this corpus cannot see

Memory spent on the **stack** is never leaked memory. Every byte count here is about the heap, so a value wrongly placed on the stack, the exact hazard that any "this does not escape, allocate it on the stack" optimization creates, passes this corpus while corrupting whatever reuses the frame.

That blindness stopped being theoretical: the `array-pushed-inside-a-loop` case crashed the program at two hundred thousand iterations while this corpus reported it clean, and correctly so. It was `alloca` inside a loop body, about thirty-two bytes an iteration against a thread's eight megabytes. Nothing leaked; the stack simply ran out.

So the runs now set `detect_stack_use_after_return=1`. Two things make that meaningful rather than decorative: the generated code is *instrumented* by clang, not merely linked against the sanitizer runtime (22 `__asan_stack_malloc` calls in a small program) and the detection was confirmed against a positive control, a C program returning the address of a local, which the sanitizer misses with the option off and reports with it on.

It is still not a guarantee. A stack value that escapes is only caught when something actually reads it after the frame dies, and this corpus's cases have to be written to do that.

## Measurement traps

Three ways a leak figure turned out to be an artefact. All three cost real time:

1. **An empty `main`.** A program that allocates nothing reports zero, and `tyrus run` and `tyrus test` both pass. Check that the program produced output before believing a zero.
2. **The test binary.** `tyrus test` compiles each `*.test.tyr` file below `target/test/files/<file stem>`, a path of its own, so it neither replaces `target/<project>` nor collides with a directory created by a test moved into a subfolder. It used to replace the program artifact, and measuring the test binary by mistake reported 16 bytes where the real program leaked 6,130. **Still run `tyrus build` immediately before valgrind**, so the artifact measured is the one the build produced.
3. **The omitted summary.** With nothing outstanding, valgrind prints "no leaks are possible" and omits the summary section entirely. A parser looking for the `definitely lost` line has to read its absence as zero.

4. **A concurrent `cargo` run.** The harness builds its own compiler with the system allocator, and an ordinary `cargo test --workspace` in another terminal replaces `libtyrus_runtime.a` underneath it mid-run: every case then fails to link, with `clang failed to compile the generated IR` and nothing explaining why. Run the corpus alone.
5. **A full disk.** `scripts/sanitizers` leaves a `target/sanitizers` that reached 47 GB here, and the first symptom of running out of room was the same unexplained link failure as above. `rm -rf target/sanitizers` when the sanitizer gate is done; it is rebuilt on demand.

4. **A corpus of isolated cases.** Every one of the fifteen cases here reported zero errors for a change that aborted the examples aggregator on startup with a double free. Each case exercises its category alone, and none of them passed an array literal to a callee. **A green corpus is not a green build**: run the complete workspace verification before believing a change to ownership is safe.

A fifth, about method rather than tooling: the aggregate figure from running the examples once is a poor metric, because it runs each example once. A per-iteration leak barely shows there. `src/memory/examples.tyr` exists to repeat allocating work for exactly that reason, and it is what surfaced `combined-operations`, which this per-category corpus had missed, and whose cause turned out to be an array literal used as a method receiver, a shape every isolated case had accidentally avoided.
